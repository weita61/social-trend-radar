## 1. 現状把握

このシートは分析専用ではなく、次の制作運用全体を持つ。

```text
構成案ストック
  ↓ 採用
制作PJ
  ↓ 投稿
成果記録（翌日 / 3日後 / 1週間後）
  ↓
型別集計
  ↓
次の構成案へ還元
```

確認したタブ:

- 使い方
- 構成案ストック
- 制作PJ
- 成果記録
- 素材管理
- ハッシュタグ
- 担当者別進捗
- 型別集計
- 型テンプレ
- リファレンス
- 設定

既存の重要な依存:

- `構成案ストック.型`は`型テンプレ`をプルダウン参照。
- `制作PJ`は元構成案Noからタイトル・型を引き継ぐ。
- `成果記録`は投稿翌日・3日後・1週間後の3行構成。
- 保存率、エンゲージ率、判定は数式列。
- `型別集計`は1週間後の成果記録から平均リーチ、平均保存率、◎数を計算。
- 担当者・進捗・判定基準は`設定`を参照。

## 2. 結論: CSVではなくGAS

CSVは初回移行・障害時の手動復旧用として残し、通常連携には使わない。

| 観点 | CSV | GAS |
|---|---|---|
| 導入 | 簡単 | 初回設定が必要 |
| 日常運用 | 毎回書き出し・取込 | 自動またはメニュー1回 |
| 重複防止 | 人が管理 | `trend_id`でupsert |
| 成果の逆連携 | 別CSVが必要 | 自動でツールへ戻せる |
| 数式・入力規則保護 | 誤貼付リスク | 書込範囲を固定できる |
| 担当者負担 | 継続的に発生 | 初回整備後は小さい |

GASは5分間隔の時間トリガー、またはスプレッドシートのカスタムメニュー「Trend Radar同期」で実行する。

## 3. 連携境界

```text
Social Trend Radar
  │ GET 採用候補 / cursor付き
  ↓
GAS
  ↓ upsert by trend_id
Radar取込タブ
  │ 人が「構成案へ採用」
  ↓
構成案ストック → 制作PJ → 成果記録
                              │
                              └─ GAS POST → Social Trend Radar
                                             owned_outcomes
```

シートをTrend Radarの収集DBにはしない。役割を分ける。

- Trend Radar: 外部トレンドの観測、根拠、構造分析、採用候補
- スプレッドシート: 自分たちの企画、担当、制作進行、投稿後成果

## 4. 事務担当へ依頼する変更

### 4-1. 新規タブ `Radar取込`

以下の列をこの順で作成する。

| 列 | 項目 | 入力元 |
|---|---|---|
| A | Trend ID | GAS、自動、編集禁止 |
| B | 同期日時 | GAS、自動 |
| C | 連携ステータス | 未確認 / 構成案へ採用 / 見送り |
| D | トレンド名 | GAS |
| E | ライフサイクル | emerging / accelerating / mainstream / cooling |
| F | 広域スコア | GAS |
| G | 確信度 | GAS |
| H | 独立投稿者数 | GAS |
| I | 確認媒体 | YouTube / Instagram / TikTok |
| J | 代表投稿URL | GAS |
| K | 表層記号 | GAS |
| L | 表現構造 | GAS |
| M | 根底欲求 | GAS |
| N | 推奨フック | GAS |
| O | 推奨構成 | GAS |
| P | 推奨CTA | GAS |
| Q | 音源 | GAS |
| R | 想定尺 | GAS |
| S | Radar詳細URL | GAS |
| T | 担当メモ | 人が入力 |

GASが更新してよいのはA:B、D:S。CとTは人が入力し、再同期で上書きしない。

### 4-2. `構成案ストック`に3列追加

- `Radar Trend ID`
- `Radar詳細URL`
- `トレンド構造`

既存の`型`は制作チームの型分類として残す。Trend Radarの「表現構造」と混ぜない。

### 4-3. `制作PJ`に2列追加

- `投稿URL`
- `Radar Trend ID`

`投稿URL`がないと、成果記録をSNS上の投稿・採用トレンドへ戻せない。`Radar Trend ID`は元構成案から自動参照する。

### 4-4. 変更しないもの

- 通し番号の形式 `A-xxx / R-xxx / K-xxx`
- 既存の型プルダウン
- 成果記録の保存率・エンゲージ率・判定式
- 担当者別進捗と型別集計
- 設定タブの既存値

## 5. GAS仕様

### 5-1. Tool → Sheet

- `GET /v1/integrations/google-sheets/trends?cursor=...`
- `trend_id`をキーに`Radar取込`へupsert。
- 既存行のC列`連携ステータス`とT列`担当メモ`は上書きしない。
- C列が`構成案へ採用`へ変わったら、構成案ストックへ1回だけ追加。
- 追加済みTrend IDはScript Propertiesで記録し、二重登録を防ぐ。

### 5-2. Sheet → Tool

- 1時間ごと、または手動同期時に`成果記録`を送信。
- `記録No`をidempotency keyにしてupsert。
- `制作PJ.投稿URL`と`Radar Trend ID`を結合して送る。
- 送信先は`POST /v1/integrations/google-sheets/outcomes`。
- 保存率・エンゲージ率・判定はシートの計算結果をそのまま送る。

### 5-3. セキュリティ

- 共有secretはセルに置かずGASのScript Propertiesへ保存。
- Cloudflare Worker側ではsecretを環境変数に保存。
- リクエストにtimestamp、body hash、HMAC署名を付ける。
- 失敗時はデータを消さず、次回同期で再送する。

## 6. CSVの位置付け

以下の2種類だけ実装する。

- `trend_candidates.csv`: Trend Radarから採用候補を書き出す。
- `owned_outcomes.csv`: 成果記録を再取込する。

通常運用には使わず、GAS障害時のバックアップとデータ持ち出し保証にする。

## 7. 管理画面の公開

構成:

```text
GitHub repository
  ↓ push
Vercel: 静的フロントエンド
  ↓ /api/* rewrite
Cloudflare Worker: API / 認証 / D1
  ↕
Mac worker: SQLite正本 / 分析 / 自動巡回
```

### Vercelで持つもの

- Next.jsまたはAstroの静的画面
- Git連携によるPreview / Production deploy
- `/api/*`をCloudflare Workerへ送るrewrite

### Vercelで持たないもの

- SQLite / DuckDB
- SNS巡回処理
- 長時間分析
- Jev API key
- D1への直接接続

Vercel Hobbyは公式上、個人・非商用利用限定。この活動が学生団体・非商用運用である間はGit経由のHobby deployを使える。営利事業、受託、販売ツールとして使う段階ではHobbyを継続せず、Cloudflare Pagesへ移すかVercel Proへ変更する。

## 8. 完了条件

- 同じTrend IDを何度同期しても行が増えない。
- 人が入力した連携ステータスと担当メモをGASが上書きしない。
- 構成案へ採用した項目だけ既存制作フローへ入る。
- 投稿URLとTrend IDを介して、成果が元トレンドへ戻る。
- GAS停止中もCSVで復旧できる。
- スプレッドシートの既存数式、入力規則、通し番号を壊さない。
