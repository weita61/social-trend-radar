# Social Trend Radar 基本設計 v1

**状態**: 構成図承認済み／詳細仕様はレビュー待ち  
**作成日**: 2026-10-09

## 1. 設計の核

収集時には幅を狭めず、全投稿に出典と観測レーンを持たせる。トレンド認定後に初めて、本人・ブランド・案件ごとの活用適合スコアを掛ける。

```text
観測レーン → 1タップ収集 → 投稿・観測値の保存 → 3層クラスタ
          → 広域トレンド認定 → 活用適合評価 → 投稿企画 → 成果学習
```

## 2. データモデル

初期DBはSQLite。分析用クエリが重くなった段階でDuckDBを併用する。

### 2-6. clusters / cluster_members

`clusters` は surface / format / desire の階層と親クラスタを持つ。`cluster_members` は投稿とクラスタの関係、距離、追加時刻を持つ。既存分類へ合わない投稿は `novelty_candidate=true` として残す。

### 2-7. trend_score_snapshots

| 列 | 内容 |
|---|---|
| velocity_score | 時間当たり増加の同条件内順位 |
| surprise_score | 投稿者通常値からのロバストな上振れ |
| diffusion_score | 独立クリエイターへの伝播 |
| cross_lane_score | 複数観測レーンでの確認 |
| cross_platform_score | 複数SNSでの確認 |
| engagement_score | 取得可能な反応品質 |
| freshness_score | 発生からの時間 |
| universal_score | 広域トレンドスコア |
| evidence_count | 判定根拠件数 |
| confidence | データ欠損を反映した確信度 |

### 2-8. fit_profiles / fit_scores / owned_outcomes

- `fit_profiles`: 対象市場、ブランド制約、利用媒体、制作能力を定義。
- `fit_scores`: トレンド×fit profileの再現性、ブランド適合、対象適合を保持。
- `owned_outcomes`: 採用した企画と自社投稿結果を保持し、適合スコアの検証に使う。

### 2-9. bias_audit_snapshots

Botや拡張機能から人が選んで送った投稿は、市場全体の無作為標本ではない。チームの関心を測る材料として保存しつつ、広域トレンドの根拠へ入れる前に偏りを監査する。

| 列 | 内容 |
|---|---|
| cluster_id | 対象クラスタ |
| observed_at | 監査日時 |
| user_submitted_share | 根拠候補のうち人が選んで送った比率 |
| submitter_hhi | 送信者への集中度。匿名IDで算出 |
| independent_confirmation_ratio | 自動巡回・公式ソースで独立確認できた比率 |
| non_user_lane_count | 人手送信以外で確認できた観測レーン数 |
| independent_creator_count | 重複を除いた独立投稿者数 |
| bias_risk_score | 0〜100。高いほど選択バイアスが強い |
| bias_label | low / medium / high |
| score_cap | 広域スコアへ適用する上限 nullable |
| explanation_json | 内訳と警告理由 |

初期式は次を校正前の仮置きとする。

```text
bias_risk =
  0.35 × user_submitted_share
  + 0.25 × normalized_submitter_hhi
  + 0.25 × (1 - independent_confirmation_ratio)
  + 0.15 × (1 - non_user_lane_coverage)
```

各入力を0〜100へ正規化する。同一URLを複数人が送った場合、`capture_event`は全件残すが投稿証拠は1件として扱う。送信回数は`team_interest_score`だけへ加算し、`diffusion_score`や独立投稿者数へ加算しない。

## 3. Bot保存フロー

```text
リンク受信
  ↓
対応URLか判定
  ├─ 非対応 → URLだけ保存し「手動確認待ち」
  └─ 対応
       ↓
URL正規化・投稿ID抽出
       ↓
既存投稿を検索
  ├─ 既存 → capture_eventだけ追加
  └─ 新規 → platform adapterで許可された情報を取得
       ↓
post / creator / 初回snapshot / capture_eventを保存
       ↓
Bias Audit待ちの候補として登録
       ↓
「保存済み・独立確認待ち」＋任意のクイックボタンを返信
```

### Bot返信案

```text
保存しました：Instagram Reel

発見場所
[FYP] [検索] [固定観測] [友人から] [公式ランキング]

気になった点
[冒頭] [企画] [音源] [編集] [コメント欄]
```

リンク送信だけで保存は完了する。追加入力は任意。音声メモが来た場合は文字起こし後、原音を保存しない設定を初期値とする。

## 4. Chrome拡張UI

Manifest V3。権限は `activeTab`、`storage`、収集APIのhost permissionを基本とする。常時ページ監視は行わない。

### 操作

- ツールバーアイコン、右クリック「Trend Radarへ保存」、`Alt+S` の3入口。
- 押した瞬間にURLをキューへ入れ、ネットワーク失敗時はローカル再送。
- 保存成功後は右下に小さなトーストのみ表示。

### ポップアップ

```text
┌──────────────────────────┐
│ Trend Radarへ保存       │
│ Instagram Reel          │
│ @creator                │
├──────────────────────────┤
│ 発見: [FYP ▾]           │
│ 注目: [冒頭] [企画] ... │
│ メモ: 任意               │
├──────────────────────────┤
│      保存済み ✓          │
└──────────────────────────┘
```

DOMから取得する情報は、明示操作時の表示値に限定し、各値へ `data_source=user_visible` を付ける。取得失敗してもURL保存は成功させる。

## 5. API境界

### POST /api/captures

入力:

```json
{
  "url": "https://...",
  "captureChannel": "bot",
  "sourceLane": "personalized",
  "discoverySurface": "fyp",
  "reason": "hook",
  "note": null,
  "visibleMetrics": null
}
```

返却:

```json
{
  "captureId": "cap_...",
  "postId": "post_...",
  "platform": "instagram",
  "deduplicated": false,
  "metadataStatus": "partial",
  "evidenceStatus": "bias_audit_pending",
  "saved": true
}
```

### GET /api/posts/:id

投稿、収集経路、時系列数値、分類結果、所属クラスタを返す。

### GET /api/trends

期間、プラットフォーム、観測レーン、階層、最低確信度で絞る。広域スコア、チーム内注目度、活用適合スコア、Bias Auditを別フィールドで返す。各クラスタには正規URL、証拠役割、観測値、最終確認日時を持つ代表投稿を最大6件含める。

## 6. トレンド認定

初期ゲート:

- 独立クリエイター3以上
- 人手送信以外の観測レーン2以上
- 自動巡回または公式ソースによる独立確認1件以上
- 時系列2点以上で増加
- 転載集中率が上限未満
- 共通する表層記号または表現構造が存在

Bias Auditの扱い:

- 0〜39: 独立確認済みなら通常どおりスコアへ反映
- 40〜69: 「暫定・バイアス注意」として表示し、確信度を減衰
- 70〜100: 「チーム内注目」に隔離し、広域ランキングのスコア上限を39とする
- ユーザーが手入力した再生数は市場証拠に使わず、媒体表示値または公式APIのsnapshotを別途取得する

数値は300〜500件の正解ラベル取得後に調整する。固定の絶対再生数は条件にしない。
